Project Overview
What we're building, why Sonnet 4.6, and cost model

The Codebase Learning Agent accepts a remote repository URL, autonomously explores the codebase through structured tool calls, applies extended thinking to synthesise deep architectural understanding, and produces a self-contained interactive HTML document that makes any codebase immediately learnable.

Why claude-sonnet-4-6 over Opus

Sonnet 4.6 supports extended thinking and delivers strong reasoning at 5× lower input cost than Opus 4.7 ($3/M vs $15/M tokens). For codebase analysis — which is heavy on file reads and pattern matching rather than open-ended creativity — Sonnet's reasoning quality is indistinguishable from Opus in practice. The thinking budget compensates for any reasoning gap. Cost per repo drops from ~$0.50 to ~$0.12.

Tool Definitions
The 6 tools the agent can call — schemas, handlers, and test stubs
Design Rationale

Tools are intentionally coarse-grained. Each returns structured JSON the model can reason over without further parsing. The agent decides what to read; it never downloads the full repo blindly. Each tool also has a clear error envelope so the model can detect partial failures and retry with a different path.

def dispatch_tool(name: str, inputs: dict, client) -> dict:
    """Route tool call to the correct RepoClient method."""
    try:
        match name:
            case "repo_metadata":
                return {"ok": True, "data": client.repo_metadata()}
            case "list_directory":
                return {"ok": True, "data": client.list_directory(
                    inputs["path"], inputs.get("depth", 2)
                )}
            case "read_file":
                return {"ok": True, "data": client.read_file(inputs["path"])}
            case "search_code":
                return {"ok": True, "data": client.search_code(
                    inputs["pattern"],
                    inputs.get("file_glob", "*"),
                    inputs.get("max_results", 20),
                )}
            case "get_commits":
                return {"ok": True, "data": client.get_commits(inputs.get("n", 10))}
            case "find_entrypoints":
                return {"ok": True, "data": client.find_entrypoints()}
            case _:
                return {"ok": False, "error": f"Unknown tool: {name}"}
    except Exception as exc:
        return {"ok": False, "error": str(exc)}

Agentic Loop Design
Extended thinking + tool use — annotated implementation
sequenceDiagram participant U as User CLI participant A as Agent (Python) participant C as claude-sonnet-4-6 participant T as Tool Layer U->>A: repo_url A->>C: messages=[system+user], tools, thinking={budget:8000} Note over C: 🧠 Extended thinking
Plans exploration strategy loop Up to 30 rounds C-->>A: tool_use block(s) A->>T: dispatch (parallel if multiple blocks) T-->>A: tool result JSON envelopes A->>C: messages += [assistant(+thinking), tool_results] Note over C: 🧠 Reason over results,
decide next tools or stop end C-->>A: text block (final AnalysisOutput JSON) A->>A: validate via Pydantic A->>A: render HTML A-->>U: report.html + cost summary
pythonagent/loop.py
import anthropic, json, pathlib
from .tools import TOOLS, dispatch_tool
from .models import AnalysisOutput, validate_output

client = anthropic.Anthropic()

SYSTEM_PROMPT = pathlib.Path("prompts/system.md").read_text()

def run_agent(repo_url: str, thinking_budget: int = 8000) -> AnalysisOutput:
    from .github_client import RepoClient
    repo_client = RepoClient(repo_url)

    messages: list[dict] = [
        {"role": "user", "content": f"Analyse this repository: {repo_url}"}
    ]

    for round_num in range(30):
        response = client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=16000,
            thinking={"type": "enabled", "budget_tokens": thinking_budget},
            system=[{
                "type": "text",
                "text": SYSTEM_PROMPT,
                "cache_control": {"type": "ephemeral"},   # cache system prompt
            }],
            tools=TOOLS,
            messages=messages,
        )

        # Forward the full assistant turn — thinking blocks MUST be preserved
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason == "end_turn":
            for block in reversed(response.content):
                if block.type == "text":
                    return validate_output(json.loads(block.text))
            raise ValueError("end_turn with no text block")

        # Dispatch all tool calls (potentially parallel)
        tool_results = [
            {
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": json.dumps(
                    dispatch_tool(block.name, block.input, repo_client)
                ),
            }
            for block in response.content
            if block.type == "tool_use"
        ]
        messages.append({"role": "user", "content": tool_results})

    raise RuntimeError("Agent did not converge within 30 rounds")
⚠️
Critical: Thinking blocks must appear verbatim in every subsequent assistant turn. Stripping them causes a 400 error from the API and breaks reasoning continuity across rounds.

Testing Strategy
50+ unit · 15 integration · 3 E2E · CI enforced at ≥85% coverage
Testing Philosophy

Three hard constraints drive the test design: (1) CI must never call the Claude API or GitHub API — cassette recording covers all network I/O. (2) The thinking-block forwarding rule must be verified mechanically, not by code review. (3) Every Pydantic field in AnalysisOutput must have a schema test — the agent produces free-text JSON and silent type coercions are a real failure mode.

Test Pyramid

E2E Tests3 tests · real APIs · marked @slow
Integration Tests15 tests · VCR cassettes · no live network
Unit Tests50+ tests · fully mocked · <5s total

class TestReadFile:
    def test_returns_decoded_content(self, mock_repo):
        mock_repo.get_contents.return_value = make_file_mock("README.md", "hello")
        client = RepoClient.__new__(RepoClient)
        client.repo = mock_repo
        assert client.read_file("README.md") == "hello"

    def test_truncates_files_over_1500_lines(self, mock_repo):
        mock_repo.get_contents.return_value = make_file_mock("big.py", FAKE_CONTENT)
        client = RepoClient.__new__(RepoClient)
        client.repo = mock_repo
        result = client.read_file("big.py")
        lines = result.splitlines()
        assert len(lines) < 800        # truncated
        assert "omitted" in result     # summary marker present

    def test_lru_cache_prevents_double_call(self, mock_repo):
        mock_repo.get_contents.return_value = make_file_mock("x.py", "content")
        client = RepoClient.__new__(RepoClient)
        client.repo = mock_repo
        # Wrap read_file with cache — call twice
        client.read_file("x.py")
        client.read_file("x.py")
        mock_repo.get_contents.assert_called_once()  # only 1 real API call

    def test_directory_listing_when_path_is_dir(self, mock_repo):
        entries = [make_file_mock("src/a.py", ""), make_file_mock("src/b.py", "")]
        mock_repo.get_contents.return_value = entries  # list = directory
        client = RepoClient.__new__(RepoClient)
        client.repo = mock_repo
        result = client.read_file("src")
        assert "src/a.py" in result
        assert "src/b.py" in result

def make_tool_use_response(tool_name: str, tool_id: str, inputs: dict):
    block = MagicMock()
    block.type = "tool_use"
    block.name = tool_name
    block.id = tool_id
    block.input = inputs
    resp = MagicMock()
    resp.stop_reason = "tool_use"
    resp.content = [block]
    return resp


def make_end_turn_response(json_payload: dict):
    block = MagicMock()
    block.type = "text"
    block.text = json.dumps(json_payload)
    thinking = MagicMock()
    thinking.type = "thinking"
    thinking.thinking = "I have finished the analysis."
    resp = MagicMock()
    resp.stop_reason = "end_turn"
    resp.content = [thinking, block]
    return resp


class TestAgenticLoop:

Scores by import frequency + commit churn + structural centrality. Ranked cards expandable to syntax-highlighted excerpts with agent annotation overlay.

Tools: find_entrypoints, search_code("router|handler|middleware|emit|subscribe")

Tools: None (uses prior analysis only)

Prompt Design
System prompt, exploration order, output schema injection

System Prompt

You are a senior software architect analysing a remote code repository. Your goal: produce a comprehensive, accurate learning document for a developer who has never seen this codebase. You have 6 tools. Use extended thinking to reason across multiple file reads before drawing conclusions. Exploration order — follow exactly: 1. Call repo_metadata and find_entrypoints in parallel — always first. 2. Call list_directory(".", depth=3) to map the full structure. 3. Read key manifests: package.json, pyproject.toml, go.mod, Cargo.toml, etc. 4. Read the README and any docs/ folder index files. 5. Use search_code to trace imports and find dominant data-flow patterns. 6. Read individual files to verify hypotheses — never guess file contents. 7. Call get_commits to score files by recent churn. Rules: - Cite every claim with the exact file path that supports it. - When README and code disagree, trust the code. - If a folder's purpose is ambiguous, read one file inside it before annotating. - You must identify exactly 10 key files, ranked 1–10. - The rebuild guide must have 4–6 phases, each with a usable Claude Code prompt. Output: When analysis is complete, output ONLY a single JSON object matching the schema below. No markdown fences, no preamble, no trailing text. // [AnalysisOutput Pydantic schema injected here at runtime]

Two-Phase Strategy for Large Repos (>500 files)

Phase 1 — Mapping (claude-haiku-4-5, no thinking)
Fast pass: repo_metadata + list_directory + get_commits. Produces a scored candidate-file list. Cost: ~$0.005.
Phase 2 — Deep Analysis (claude-sonnet-4-6, 8k thinking)
Receives Phase 1 map as context. Focuses only on ranked candidates. Produces final AnalysisOutput. Cost: ~$0.10.

Rebuild This Agent from Scratch
Ideas, phases, and copy-able prompts for vibe-coding the whole system

Core Ideas to Come Up With First

💡 Tool design IS the product
Design the 6 tools on paper before writing one line of agent code. Bad tool granularity = expensive, shallow analysis. Start with: what does the model need to know, and what's the cheapest way to retrieve it?
💡 Output schema first
Define the Pydantic model before writing the system prompt. The schema IS the spec. Every prompt decision flows from what fields the model must populate.
💡 Test the loop mechanics, not the output quality
Thinking-block forwarding, model name, round limit, parallel dispatch — these are mechanical and must be tested. Output quality is evaluated by reading the HTML, not by assertions.
💡 Cache the JSON, not the HTML
Agent produces JSON. Renderer is deterministic. Store the JSON; re-render free. This lets you iterate on the HTML template without re-running expensive API calls.
